## 1. Executive Summary

P1-05 (GRN cancellation can reverse inventory that was not received by that GRN — it subtracted "until zero" from shared stock) and P1-06 (inventory quantity mutations that read→compute→write instead of using atomic arithmetic / CAS / serialized locking, plus an `updateItem` with no optimistic-lock) are both remediated and closed.

- P1-05: GRN lines now carry an exact `inventoryBatchId` (DB-level attribution, FK `ON DELETE SET NULL`), and cancellation reverses **only** the batch row that GRN line was attributed to, using a guarded atomic decrement (`id + isActive + quantity gte` in the WHERE). Legacy null-attribution lines are skipped. Repeat cancel is idempotent; concurrent cancels serialize on the `goodsReceipt.updateMany` status claim; a lost-update race on shared batch identity is resolved at the database level with a natural-key unique index and deterministic P2002 reuse.
- P1-06: every inventory quantity mutation is now atomic arithmetic (`increment`/`decrement`), guarded CAS (`quantity gte` in the WHERE), a status claim, or proven serialized locking (`SELECT … FOR UPDATE`). `updateItem` now performs a real version CAS (`version: item.version` in the WHERE, `version: { increment: 1 }`, `ConflictException` on count 0).

Net verification: **84 suites / 1044 tests passing** (baseline 84 / 1027 → +17 new concurrency/regression tests, zero regressions), `tsc` clean, `nx lint api` clean, `nx build api` clean, `prisma validate` valid, `prisma migrate status` 24/24 up to date, live `/api/v1/health/live` returns **200** with database and redis up.

## 4. Root-Cause Analysis

| Surface               | Previous (buggy) behavior                                                                                                                                | Impact                                                                                                                                 |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `cancelGRN`           | Reversed inventory with `currentQuantity - qty` floor-at-0 arithmetic per item regardless of which GRN contributed that stock; no batch ownership model. | Cancelling GRN-A could consume stock physically received by GRN-B; history inaccurate; double-cancel could "reverse" stock never held. |
| Batch identity        | No link between a GRN line and the `InventoryBatch` row it created; batch reuse was an unguarded `findFirst → create` sequence.                          | Two concurrent receipts of the same physical batch could create duplicate batch rows (or rely on an unguarded read).                   |
| `updateItem`          | `inventoryItem.update` unconditionally overwrote quantities with a stale read.                                                                           | Two concurrent edits could silently drop one writer's quantity change (lost update).                                                   |
| Adjustments / waste   | DECREASE approval used a read→compute→write decrement without a `gte` guard.                                                                             | Concurrent consumption could drive stock negative (overdraw).                                                                          |
| Cycle-count reconcile | Applied variance by absolute read→write without a status claim or guard.                                                                                 | Reconcile could be applied twice, or force negative quantities.                                                                        |
| Transfers             | start/receive/cancel did not claim status first; item decrement was unguarded read→write.                                                                | Double-ship or double-receive of the same transfer could double-decrement.                                                             |
| Recipe deduction      | Deduction read → compute → write inside a transaction without a row lock.                                                                                | Two orders sharing an ingredient could both compute from the same base and lose one order's deduction.                                 |
